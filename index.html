Deterministic testing for distributed protocols

Test distributed protocols the way you test pure functions.

Run your own consensus code under deterministic virtual time and injected network faults. Check your invariants after every single step. When one breaks, you get the step it broke on and a trace hash that replays the identical run.

A qualified Raft implementation ships as the worked reference. Durable io_uring storage, a checksummed write-ahead log, XDP and TC kernel fault injection, Jepsen linearizability, and a bounded TLA+ model. Apache 2.0.

The leader was cut off at step 200 and the majority carried on without it. 945 messages were dropped by that partition, and the count is reported because a fault that dropped nothing would have tested nothing.

The bug you cannot reproduce

A partition arrives during an election. A node crashes between the write and the fsync. Two messages swap places on the wire. The cluster loses an acknowledged write, and by the time anyone looks, the interleaving that caused it is gone.

Promtact removes the part that makes this hard. Time is virtual, scheduling is seeded, and every message loss and delay is drawn from that seed. The same seed produces the same execution, so a failure found once is a failure you can return to.

Four things you plug in

Your protocol

Implement four methods for dst.Cluster and two for dst.Wire. The engine supplies virtual time, a seeded schedule, message loss and delay, and a reproducible execution trace.

Generic over your message type, so nothing is boxed and the hot path allocates nothing.

Your properties

A dst.Invariant is evaluated after every step. A failure comes back as a dst.Violation carrying the property name, the step, and the trace hash.

Invariants are safety properties. Progress is asserted separately, where you decide what progress means.

Your faults

Partitions, isolated nodes, one-way link failures, and time windows that open and heal on their own. Declared once, applied deterministically.

Injectors are consulted after the engine draws each message's loss and delay, so the same seed runs the same schedule with and without a fault.

Your storage

Implement wal.Device and inherit the checksummed record format, sequence validation, and torn-tail recovery of wal.Log.

A conformance suite checks the ten properties the log relies on before you trust it with consensus state.

A run is a file, not a test you have to rewrite

The seed, the topology, the faults and when they open are declared once. Anyone holding the file reproduces the run exactly, on any machine, without reading the test that produced it.

{"seed": "0x4A2C", "nodes": 5, "steps": 1200,
 "proposeEvery": 17,
 "faults": [{"type": "split",
             "a": [1], "b": [2,3,4,5],
             "start": 200, "end": 700}]}

When a property breaks, the engine stops on the step it broke on and hands back the coordinate rather than a message you have to reproduce by guesswork.

$ go run .
violated="one adopted value" step=1
trace=29f79b95c06cc89754c99c2b0ed7b107
      da682cbe28b7d728830cbb9430855c93

That output comes from the starter project promtact new generates. Its placeholder protocol is unsafe when two nodes propose at once, and the generated test suite requires the engine to catch it.

Not just Raft

The repository carries a complete single-decree Paxos implementation driven through the same engine, with its own invariants, its own scenario file, and partition campaigns across a thousand seeds. Sixty lines of adapter connect it.

Its campaigns assert that a proposer actually had to abandon its own value for one already accepted elsewhere. Across two hundred seeds that happens about three thousand times, which is the situation Paxos exists to survive.

What has been measured

Bounded model check
46,667,923 states generated, 6,121,927 distinct, state graph exhausted, no invariant violation.
Engine equivalence
7,000 paired runs compare the engine against the qualified simulator at every tick and require a bit-identical execution.
Linearizability
Jepsen with the Knossos register checker reports valid? true under leader kill and network loss.
Deterministic sweep
1,000 seeds at 1,000 steps each, run in parallel, no divergence.
Durable NVMe writes
10,000 operations at 7,971 ops/s, p50 117 us, p99 196 us, one completed FSYNC each.
Durable file writes
1,000 operations at 2,189 ops/s, p50 450 us, p99 544 us, on ext4.
Record encoding
23.34 ns per operation, zero allocations.
Kernel fault injection
XDP and TC programs load and pass the verifier and JIT; injection and cleanup are gated on every run.

Every figure names the run that produced it in EVIDENCE.md, with the host, the commit and the bounds it holds under. There has been no third-party penetration test and no SOC 2 or ISO 27001 audit.

Start

Clone it and run the suite, the non-Raft example, and a scenario:

$ git clone https://github.com/hunterinvariants/Promtact.git
$ cd Promtact
$ go test ./...
$ go test ./examples/paxos -v
$ go run ./cmd/promtact simulate \
    -config examples/leader-partition.json

Or start your own from a skeleton that builds, runs and tests immediately:

$ go run ./cmd/promtact new ../mysystem
$ cd ../mysystem
$ go mod tidy && go test ./... -v

Every command lives behind one binary. Commands that need kernel facilities a build cannot reach are absent rather than listed and failing.
