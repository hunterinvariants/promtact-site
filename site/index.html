Deterministic testing for distributed protocols

Find distributed-system failures before production does.

Turn rare race conditions, lost writes and partition failures into deterministic runs your engineers can repeat locally and in CI. When a safety property breaks, Promtact identifies the step and trace instead of leaving a production incident that cannot be reproduced.

A qualified Raft implementation ships as the worked reference. Durable io_uring storage, a checksummed write-ahead log, XDP and TC kernel fault injection, Jepsen linearizability, and a bounded TLA+ model. Apache 2.0.

The leader was cut off at step 200 and the majority carried on without it. 945 messages were dropped by that partition, and the count is reported because a fault that dropped nothing would have tested nothing.

What changes for the business

Diagnose instead of rediscover

A rare interleaving becomes a stable seed, step and trace. Engineers can return to the same failure while fixing it instead of waiting for it to happen again.

Catch correctness failures earlier

Safety invariants run after every simulated step and can expose lost writes, conflicting decisions and invalid state transitions before a release reaches customers.

Put fault campaigns in CI

Virtual time, seeded schedules and declared network faults turn protocol testing into a repeatable engineering gate rather than an occasional lab exercise.

Review evidence, not assurances

Scenarios, trace hashes, model checks and recorded qualification runs give architecture and risk reviews concrete artifacts with explicit claim boundaries.

The bug you cannot reproduce

A partition arrives during an election. A node crashes between the write and the fsync. Two messages swap places on the wire. The cluster loses an acknowledged write, and by the time anyone looks, the interleaving that caused it is gone.

Promtact removes the part that makes this hard. Time is virtual, scheduling is seeded, and every message loss and delay is drawn from that seed. The same seed and caller actions produce the same execution, so a failure found once is a failure you can return to.

Where it fits

Financial systems

Ledger, payment and transaction engines where two accepted answers or a lost acknowledged write become business-critical correctness failures.

Cloud and data infrastructure

Databases, replicated storage, key-value systems, caches and control planes that must remain safe through elections, retries and partitions.

Industrial and edge systems

Message-passing protocols operating across intermittent, delayed or one-way network links where production conditions are difficult to recreate.

Platform engineering

Internal protocol libraries and shared infrastructure that need a reusable way to define invariants, inject faults and preserve failing executions.

Four things you plug in

Your protocol

Implement four methods for dst.Cluster and two for dst.Wire. The engine supplies virtual time, a seeded schedule, message loss and delay, and a reproducible execution trace.

Generic over your message type, so nothing is boxed and the hot path allocates nothing.

Your properties

A dst.Invariant is evaluated after every step. A failure comes back as a dst.Violation carrying the property name, the step, and the trace hash.

Invariants are safety properties. Progress is asserted separately, where you decide what progress means.

Your faults

Partitions, isolated nodes, one-way link failures, and time windows that open and heal on their own. Declared once, applied deterministically.

Injectors are consulted after the engine draws each message's loss and delay, so the same seed runs the same schedule with and without a fault.

Your storage

Implement wal.Device and inherit the checksummed record format, sequence validation, and torn-tail recovery of wal.Log.

A conformance suite checks the ten properties the log relies on before you trust it with consensus state.

Cross-language protocol verification

Rust reference, checked end to end

The versioned process adapter protocol lets protocol state live in a separate operating-system process while the Go host retains virtual time, deterministic scheduling, fault injection and trace hashing. The checked Rust token-ring adapter is the first reference implementation.

This is a tested process boundary and reference adapter, not a general Rust SDK or an in-process native binding.

Commissioned C++ and Java integrations

For teams whose protocols are implemented in C++ or Java, Promtact offers scoped commercial engineering to build and qualify a process adapter around the existing implementation. A scope can include wire mapping, invariants, deterministic fault campaigns, a CI gate and a versioned evidence report.

No off-the-shelf C++ or Java SDK ships today. Deliverables, licensing, support boundaries, milestones and acceptance evidence are agreed for each engagement before implementation begins.

A run is a file, not a test you have to rewrite

The seed, the topology, the faults and when they open are declared once. Anyone holding the file reproduces the run exactly, on any machine, without reading the test that produced it.

{"seed": "0x4A2C", "nodes": 5, "steps": 1200,
 "proposeEvery": 17,
 "faults": [{"type": "split",
             "a": [1], "b": [2,3,4,5],
             "start": 200, "end": 700}]}

When a property breaks, the engine stops on the step it broke on and hands back the coordinate rather than a message you have to reproduce by guesswork.

$ go run .
violated="one adopted value" step=1
trace=29f79b95c06cc89754c99c2b0ed7b107
      da682cbe28b7d728830cbb9430855c93

That output comes from the starter project promtact new generates. Its placeholder protocol is unsafe when two nodes propose at once, and the generated test suite requires the engine to catch it.

Not just Raft

The repository carries a complete single-decree Paxos implementation driven through the same engine, with its own invariants, its own scenario file, and partition campaigns across a thousand seeds. Sixty lines of adapter connect it.

Its campaigns assert that a proposer actually had to abandon its own value for one already accepted elsewhere. Across two hundred seeds that happens about three thousand times, which is the situation Paxos exists to survive.

No local shortcut

The checked-in token-ring consumer is a separate Go module. Its go.mod pins Promtact v0.3.6, has no local replace directive, and the simulation imports only the public dst package.

The failure path crosses the boundary too

A separate negative control injects a second valid token into the real Rust process. The Rust adapter reports the declared invariant and conflicting protocol state back through the framed process protocol.

invariant="at-most-one-token"
cause="token held by nodes [1, 2]"

The complete matrix runs in CI with pinned Go and Rust toolchains. A read-only clean-room run with fresh Cargo, Go module and build caches reproduced the same result.

Deployment and trust boundary

Runs in your environment

The deterministic engine is a Go library and command-line tool for local development and CI. Core simulation runs require no hosted control plane or Promtact account.

Works inside restricted networks

Once the source or release artifacts are available inside your boundary, deterministic scenarios and replays do not depend on an external service.

Verifiable releases

Published binaries carry checksums, GitHub build attestations and public source, so teams can verify what they run before admitting it to CI.

Evidence with stated bounds

The security policy and evidence ledger state which behavior was tested, on which host and commit, and what each result establishes.

Who wrote this

Promtact is the work of one person. The same hands have five patches merged into curl and libssh2, upstream on master, through maintainer review.

Two of them free state that nothing was freeing. One is a test that pins down whether an authorisation scope survives a redirect. Those are defects that need a particular sequence before they show themselves, which is the reason the engine above exists.

How to engage

Adopt the open-source framework

Use the Apache 2.0 engine directly, start from the working protocol examples, including the checked Rust process reference, and keep simulations in the same repository and CI system as your implementation.

Discuss a scoped verification engagement

A scoped verification engagement can include a protocol adapter against the public Promtact API, safety invariants, deterministic fault campaigns, CI-ready scenarios, and a versioned evidence report with findings, trace references, claim boundaries and recommended remediation.

For a non-Go system, the first step is an adapter assessment covering process lifecycle, message schema, invariants and build constraints. A commissioned C++ or Java integration is then scoped against the published process protocol and accepted through language-specific conformance tests.

After an initial protocol walkthrough, Promtact provides a written scope, milestones and schedule based on the adapter boundary, invariants and campaign depth. Scope and deliverables are agreed before work begins.

Start

A released binary needs no Go, no compiler and no account. The installer refuses to install anything whose checksum does not match, and checks the build attestation when it can:

$ git clone https://github.com/hunterinvariants/Promtact.git
$ cd Promtact
$ less scripts/install.sh
$ ./scripts/install.sh

== checking the checksum
   ok  2d28e7e93e9eebe6b6e7bef82cecbf6fd408c6cd
       4c8c8e3d4e632b0a5c9d49d2
== checking the build attestation
   ok  built by hunterinvariants/Promtact/.github/
       workflows/release.yml@refs/tags/v0.3.6

Reading it before running it is the point, which is why there is no one-line pipe from the network into a shell. A script you have not read cannot prove anything to you, and proving where a binary came from is what this one is for.

From source instead, in that same checkout: the suite, the non-Raft example, and a scenario.

$ go test ./...
$ go test ./examples/paxos -v
$ go run ./cmd/promtact simulate \
    -config examples/leader-partition.json

Or start your own from a skeleton that builds, runs and tests immediately:

$ go run ./cmd/promtact new ../mysystem
$ cd ../mysystem
$ go mod tidy && go test ./... -v

Every command lives behind one binary. Commands that need kernel facilities a build cannot reach are absent rather than listed and failing.
