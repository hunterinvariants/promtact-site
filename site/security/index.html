Security

Last reviewed 25 August 2026

Promtact is open-source software. There is no hosted service, no account, and no data held on anyone's behalf. This page says how to report a problem, which surfaces matter, and how a release is put together.

Scope of this page

This page covers the open-source project's vulnerability policy and release security. Enterprise access control, auditability, deployment boundaries and assessment status are summarized on the Enterprise security review.

Reporting a vulnerability

Use GitHub's private vulnerability reporting on the repository, under Security, Report a vulnerability. That opens a private thread with the maintainer. Please do not open a public issue for a suspected vulnerability.

This is a one-person project. Reports are read and answered as soon as they are seen. Once a fix is released, the report may be published as a GitHub security advisory, crediting the reporter unless they prefer otherwise. The full policy is in SECURITY.md.

Supported versions: the latest tag only. There are no backports.

What is worth reporting

The parts where someone else's bytes or privileges are involved.

SurfaceWhy it matters
The wire formatprotocol decodes CRC32C-framed messages from a socket. A crash, hang, or unbounded allocation reachable from a malformed frame is a denial of service against a consensus node.
The durable formatstorage/wal parses records and recovers torn tails from disk. Relevant if a node can be made to accept a crafted log.
The chaos controllerchaos runs privileged network commands. A dedicated promtact-chaos namespace, promtact-* veth names, address and rate validation, and explicit ownership checks keep faults away from existing resources and management interfaces. A way around any of them is a real finding.
The raw block-device benchmarkpromtact raw-bench refuses to write without a canonical /dev/ path, an exact expected size, and an explicit ERASE: confirmation. A way to make it write to the wrong device is a real finding.
Release artifactsAnything that would let a published binary, SHA256SUMS, or the build attestation misrepresent what it is.

What is not a vulnerability

CaseWhy
The placeholder protocol in promtact newIt is deliberately unsafe when two nodes propose at once, and the generated test suite requires the engine to catch it. That is the lesson, not a defect.
Running the chaos controller against a real interfaceIt refuses by design. Disabling the guards and then reporting the result is not a finding.
A documented bound on a correctness claimEVIDENCE.md states what each result establishes and what it does not. If a documented bound is wrong, that is worth reporting - with the measurement that shows it.

How a release is built

The wire format is fuzzed. Four Go fuzz targets cover frame reading and message decoding. They run in CI on every change and in a longer nightly campaign.

Known vulnerabilities block the release. A release gate runs govulncheck with reachability analysis and refuses to publish while anything reachable is outstanding. The Go toolchain is pinned in go.mod for that reason rather than for language features.

Releases carry provenance. Each one ships a Sigstore keyless build attestation and an SPDX software bill of materials, alongside SHA256SUMS. The attestation says more than a checksum does: it names the workflow, the repository and the tag that produced the file.

$ gh attestation verify promtact-v0.3.6-linux-amd64 \
    --bundle bundle.json --repo hunterinvariants/Promtact
✓ Verification succeeded!

- Attestation #1
  - Build repo:..... hunterinvariants/Promtact
  - Build workflow:. .github/workflows/release.yml@refs/tags/v0.3.6

The bundle is public, so checking it needs no GitHub account. The commands, including how to fetch the bundle, are in SECURITY.md. A downloaded binary also reports its own tag, commit and toolchain through promtact version, because a file name is not evidence.

Dependencies are kept few on purpose. The library and its commands build against the standard library. A smaller dependency graph is fewer places for someone else's compromise to become yours.

Running it safely

The chaos controller and the raw block-device benchmark do real, privileged things to the machine they run on. Use them only on a dedicated test host, inside the namespace and veth pair the controller creates, and never attach a fault policy to a management interface. See bpf/README.md.

This website

The site is static, served from Cloudflare Pages. Its content security policy is default-src 'none': no scripts, no fonts, no images from anywhere else, no third-party requests of any kind. Machine-readable contact details are at /.well-known/security.txt.
